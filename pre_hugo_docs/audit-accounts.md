# Account, admission, history, and live-configuration audit

This audit traces complete admission, interactive login and registration, account history, and live runtime-directive paths against the C server. The comparison used the C source in `btmux-khi/src/mux` and isolated copies of `tests/fixtures/game`. It did not write a production game or database and did not restart a production process.

## Evidence

The paired TCP probe `tests/tools/admission_probe.py` was executed against isolated C and Rust worlds before and after remediation. The checked-in transcripts are `tests/fixtures/admission-audit-before.json` and `tests/fixtures/admission-audit-after.json` (the original before run also remains at `/tmp/admission-audit-before.json`). It seeded three failed logins with a fixed host and timestamp, changed `max_players` while connected, then exercised registration at the exact limit and an existing-player login. The after run shows matching failure count/host/time, confirmation prompts, registration at equality, registered identity, and rejection of the later existing login at capacity. Focused Rust tests cover the repaired branches and all-session routing. Rows marked source evidence were traced through the named C and Rust functions without claiming a paired transcript for every directive value.

## Retained differences and limits

Rust commits account changes atomically and leaves an unsaved login unchanged. C account storage APIs can report individual write failures after other connection effects have occurred; Rust retains the approved transaction and rollback model rather than publishing partial persistent state.

Rust records a bounded, safe peer descriptor in `last_site` and reports it as literal text. It does not reproduce C's optional `username@host` site string or interpret host text as markup. Passwords remain absent from diagnostics and command responses.

C keeps four successful and three failed history rows. Rust has a configurable total `login_history_limit`. On load Rust preserves each outcome's position order and merges the two queues by timestamp for ordinary chronology, so reducing the total limit does not systematically favor one outcome. The schema has no cross-outcome insertion sequence, so equal timestamps or a clock moving backward across outcomes leave their exact global insertion order unrecoverable. Per-outcome `@last` display order remains exact even across backward clocks.

The paired execution covers the two observed admission/login discrepancies and prompt text. Other live-configuration conclusions are source traces backed by existing Rust tests, not byte-for-byte differential runs of every directive, access edit, reload timing, or failure injection.
